# 글러트니 개발 프로세스

> 이 문서는 5.1절의 글쓰기 규칙을 따른다.
> 용어는 [glossary.md](glossary.md)를 따른다.

## 1. 개요

- 제품: 링크를 텔레그램 봇으로 저장하고, 소비할 때까지 다시 보여주는 봇.
- 이름: 글러트니 (Gluttony).
- 레포: `gluttony` (공개).
- 봇 사용자명 후보: `@gluttony_digest_bot` (BotFather 확인 전).
- 스택: 13절 참고 (2026-10-17 확정).
- 운영 방식: 구현은 에이전트(Claude Code)가 대부분 맡는다. 사람은 판단하고, 감독하고, 이해한다.

## 2. 원칙

1. 앞 단계가 커밋한 파일을 다음 단계가 읽는다. 커밋 기록이 의사결정 기록이 된다.
2. 사람은 "무엇"과 "왜"를 정한다. 에이전트는 "어떻게"를 맡는다.
3. 사람의 주의는 되돌리기 비싼 결정에 쓴다.
4. 계획 문서를 만드는 것과 이해하는 것은 다르다. 사람이 이해하기 좋은 결과물을 만든다.
5. 에이전트는 스스로 검증할 수 있어야 한다. "완료"는 검사 통과를 뜻한다.
6. 위험한 동작은 프롬프트가 아니라 훅으로 막는다.

## 3. 산출물과 폴더 구조

```
gluttony/
  CLAUDE.md                 # 에이전트용 맥락. 한 페이지 이하.
  REVIEW.md                 # PR 리뷰 기준과 리뷰 묶음 형식.
  docs/
    process.md              # 이 문서.
    glossary.md             # 허용 용어집.
    architecture.md         # 코드에서 생성한 다이어그램과 데이터 흐름.
  intents/
    NNNN-slug/
      intent.md             # 무엇을, 왜, 어떤 제약에서. 20줄 이하.
      spec.md               # 요구사항, 시나리오, 결정 필요 항목. 1~2쪽.
      plan.md               # L 등급만.
  .claude/
    settings.json           # 훅, 권한.
    agents/                 # verifier 등 서브에이전트.
    skills/                 # writing, explain-system 등.
  src/
    core/                   # 순수 로직. 플랫폼 코드에 의존하지 않는다.
    adapters/               # telegram, d1, oembed.
    worker.ts
  test/fixtures/            # 실제 텔레그램 업데이트 JSON.
  migrations/
```

- 현재 동작의 기준은 테스트다. 테스트 이름에 spec의 시나리오 ID를 넣는다.
- spec은 머지 전까지 고칠 수 있다. 머지된 spec과 테스트는 실제 동작과 일치해야 한다.

## 5. 이해 장치

### 5.1 글쓰기 규칙 (STE 80%)

- 한 문장에 한 사실만 쓴다.
- 능동형으로 쓴다.
- 문장을 짧게 끊는다.
- 용어는 `docs/glossary.md`에 있는 단어만 쓴다.
- 문서와 코드는 같은 용어를 쓴다.
- 적용 대상: intent, spec, plan, PR 설명, 커밋 메시지, 코드 주석.
- 구현: CLAUDE.md에 핵심 규칙 몇 줄. 자세한 규칙은 `writing` 스킬.

용어집은 [glossary.md](glossary.md)에 있다.

### 5.2 다이어그램은 코드에서 생성

- 항목 상태 전이를 코드에 데이터로 정의한다.
- 스크립트가 그 데이터로 mermaid 다이어그램을 만든다. LLM이 그리지 않는다.
- 생성 결과는 `docs/architecture.md`에 커밋한다.
- CI는 다이어그램이 코드와 일치하는지 검사한다.

### 5.3 HTML로 동작 보기

- 대화 재생: fixture 재생 결과를 텔레그램 대화 화면처럼 HTML로 만든다.
- 시뮬레이터: 재노출 점수처럼 감이 오지 않는 로직은 일회용 페이지로 확인한다.
- 시스템 설명: `/explain-system` 스킬이 현재 코드로 설명 페이지를 만든다. PR 5개 머지마다, 또는 오랜만에 돌아왔을 때 쓴다.

### 5.4 설명 영상

- 보류한다. README 데모가 필요할 때 다시 검토한다.

### 5.5 오래 남길 것과 쓰고 버릴 것

| ------------------------------------- | --- | ------- | --- |
| 요약 3~5줄 (글쓰기 규칙 적용)         | ✅  | ✅      | ✅  |
| 에이전트가 스스로 정한 가정·결정 목록 | ✅  | ✅      | ✅  |
| 검사 결과 (`npm run check`)           | ✅  | ✅      | ✅  |

- main 브랜치 보호: PR 필수, 검사 통과 필수.

## 7. 피드백 루프와 훅

- 단일 검사 명령: `npm run check` (타입체크, 린트, 테스트, 다이어그램 일치).
- 편집 후 훅: 포맷, 타입체크.
- 차단 훅:
  - 토큰과 `.dev.vars`가 diff에 들어가는 것.
  - 적용된 마이그레이션 파일 수정.
  - 버그 수정 중 테스트 파일 수정.
- 승인 게이트 훅: `wrangler deploy`, 원격 D1 마이그레이션, `wrangler secret`.
- 서브에이전트: `verifier` — fixture를 재생하고 결과만 보고한다. 고치지 않는다.
- 스킬은 사이클 2~3회 뒤에 만든다. 처음에는 손으로 해 본다.

## 8. 배포와 환경

- Claude는 로컬에서 직접 배포하지 않는다. 훅이 `wrangler deploy`를 막는다.
- main 머지 → GitHub Actions → dev 봇 배포 → fixture 재생으로 자동 점검.
- 등급별 prod 배포 (2026-10-17 결정):
  - S, M: 점검을 통과하면 prod에 자동 배포한다. PR 머지가 사람의 승인이다.
  - L: prod 배포와 원격 D1 마이그레이션은 GitHub Environment 승인 버튼을 눌러야 진행한다.
- 롤백: Worker 코드는 `wrangler rollback`으로 되돌린다. D1 마이그레이션은 되돌릴 수 없으므로 L로 다룬다.
- dev 봇과 prod 봇을 나눈다. dev 봇에는 main만 배포한다.
- 시크릿은 `wrangler secret`으로만 넣는다. 사람이 직접 입력한다.

## 11. 결정 사항 (2026-10-16)

1. 등급 결정: 규칙이 최소 등급을 정한다. Claude가 등급과 근거를 제안한다. 사람이 spec 확인 때 확정한다. S는 PR에서 확정한다.
2. M과 L의 경계: 아래 목록 중 하나라도 있으면 L이다.
   - D1 스키마·마이그레이션
   - callback_data 형식 (이미 보낸 메시지의 버튼이 깨진다)
   - 사용자에게 보이는 명령어 이름
   - 데이터를 지우는 동작
   - 비용이 생기는 변경
3. 작업 중 등급 상승: 멈춘다. L로 올린다. plan.md를 쓰고 확인받은 뒤 재개한다.
4. 등급 강제: PR 라벨(`tier:S|M|L`) + CI 검사. 위 목록에 해당하는 파일을 바꿨는데 `tier:L` 라벨이나 plan.md가 없으면 CI가 실패한다.
5. PR 리뷰: 처음에는 PR 전에 세션에서 로컬 리뷰를 한다. 흐름이 안정되면 claude-code-action을 추가한다.
6. 봇 이름: prod `gluttony_digest_bot`, dev `gluttony_digest_dev_bot` (BotFather 확인 전).
7. 세션 하나 = intent 하나. spec 승인은 머리말 기록. 브랜치는 `intent/NNNN-slug`, `fix/slug`. 머지 후 회고. 모두 동의.

## 12. 서비스 동작 결정 (2026-10-17)

- 항목 상태: 쌓임, 미룸, 먹음, 뱉음, 보관. "보여줌"은 상태가 아니라 기록이다.
- 되돌리기: 처리한 메시지에 되돌리기 버튼을 남긴다. 다음 다이제스트 전까지 동작한다. 이전 상태를 함께 저장한다.
- URL 추출: entities(`url`, `text_link`) 기준으로 뽑는다. 여러 개면 첫 번째만 저장한다.
- URL 정규화: 플랫폼별 규칙 표를 spec에 둔다. 원본 URL도 함께 저장한다.
- 다이제스트 알림: 헤더만 소리, 항목 메시지는 무음.
- 저장 시 우선순위: 내 메시지에 🔥 반응 = 우선순위 높음.
- 중복 링크: 🤝 반응 + 우선순위 한 단계 올림. 보관된 항목이면 쌓임으로 되살린다.
- 미루기: 내일 / 주말 / 다음 주.
- 항목 0개인 날: 다이제스트를 보내지 않는다.
- 30일 정리: 일요일에 묻는다. 하나씩 보기 / 모두 보관 중 고른다. 지우지 않는다.
- 다이제스트: 매일 21시, 3개.

## 13. 기술 스택 (2026-10-17 확정)

기준: 혼자 운영할 수 있을 것. 무료일 것. 대중적이어서 에이전트가 잘 알 것.

| 층            | 선택                                       | 이유                                                             |
| ------------- | ------------------------------------------ | ---------------------------------------------------------------- |
| 언어          | TypeScript (strict)                        | Workers가 기본으로 지원한다. 타입이 에이전트의 실수를 잡는다.    |
| 봇 프레임워크 | grammY                                     | TS 텔레그램 봇에서 가장 많이 쓴다. Bot API 타입이 최신이다.      |
| 런타임        | Cloudflare Workers                         | 서버 관리가 없다. 무료로 하루 10만 요청. 웹훅 HTTPS 기본 제공.   |
| DB            | D1 (SQLite)                                | SQL 조회가 쉽다. 마이그레이션 도구가 있다. SQLite라 옮기기 쉽다. |
| 쿼리 계층     | 직접 쓴 SQL + 얇은 저장소 계층             | 테이블이 적다. 마이그레이션을 사람이 리뷰하기 쉽다.              |
| 스케줄러      | Cron Trigger 1개                           | 매일 12:00 UTC. 일요일이면 주간 정리를 함께 한다.                |
| 테스트        | vitest + `@cloudflare/vitest-pool-workers` | 실제 Workers 런타임에서 D1과 함께 로컬로 돈다.                   |
| 린트·포맷     | ESLint (typescript-eslint) + Prettier      | 대중성을 우선한다.                                               |
| CI·배포       | GitHub Actions + wrangler                  | Environment 승인으로 L 등급 prod 게이트를 만든다.                |

원칙:

- `core/`는 순수 TS로 둔다. Cloudflare 전용 코드는 `adapters/`에만 둔다.
- 의존성은 최소로 둔다. 버전을 고정하고 lockfile을 커밋한다.
- 무료 플랜의 요청당 CPU 10ms 제한 때문에 HTML 파싱은 하지 않는다. 메타데이터는 oEmbed(JSON)만 쓴다.

나중에 검토할 것:

- Durable Objects (SQLite): 미루기 만료를 정확한 시각에 처리해야 할 때.
- Drizzle: 스키마가 커질 때.

ADR로 남길 것: `0001-telegram-grammy`, `0002-workers-d1`, `0003-eslint-prettier`.

## 14. 작업 환경 (인터뷰)

- 작업은 데스크톱 Claude Code에서 한다. 리뷰와 승인은 휴대폰에서도 한다.
  - 리뷰 묶음과 대화 재생은 휴대폰 GitHub 앱에서 읽혀야 한다.
- intent를 2~3개 병렬로 진행한다.
  - intent마다 worktree를 쓴다.
  - dev 봇 웹훅은 하나뿐이다. 브랜치 확인은 fixture 재생으로 하고, dev 봇에는 main만 배포한다.
- PR 하나 리뷰에 15분 정도 쓴다. 리뷰 묶음 분량을 여기에 맞춘다.
